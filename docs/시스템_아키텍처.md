## 1. 시스템 철학

Regula는 단순 챗봇이 아니다. **의료기기 인허가를 위한 팩트 기반 전문 가이드 시스템**이다.

### 핵심 원칙

| 원칙 | 내용 |
|------|------|
| **팩트 기반** | MD-process·ra-project에 존재하는 사실만 출처 명시하여 답변. 추측·해석·창작 없음 |
| **구조적 hallucination 차단** | Agent는 탐색·라우팅만 수행. 찾은 문서 외 내용은 절대 생성하지 않음 |
| **단일 답변 구조** | 사용자 역할(일반 직원·RA 담당자·경영진) 무관하게 동일한 팩트 + 출처 구조 |
| **지식의 자기 강화** | 사용자 질문 → 미답변 → 지식베이스 보강 → 이후 답변 가능의 순환 사이클 |

## 4. Agent + Bot 역할 분리

### Agent (탐색·라우팅 전담)

- 사용자 질문 수신
- MD-process·ra-project 문서 탐색
- 관련 문서 후보 선별 및 Bot에 전달
- **답변 생성 절대 불가** — 찾은 문서만 전달

기술: Hermes Agent / Claw류 접목 가능

### Bot (팩트 답변 전담)

- Agent가 전달한 문서만 근거로 사용
- 출처(레포 경로·문서명·조항) 명시
- 찾은 내용 외 추가 생성 없음
- 미답변 시 명확히 고지

### 답변 구조 (모든 사용자 공통)

```
[답변]
내용: {MD-process 또는 ra-project에서 찾은 팩트}
출처: {레포명 > 폴더 > 문서명 > 조항}
신뢰: {내부 문서 기반 / 외부 공식 소스 기반}
```

## 5. 미답변 처리 파이프라인

Bot이 내부에서 답변을 찾지 못했을 때의 처리 흐름이다.

```
사용자 질문
    │
    ▼
Agent 탐색 (MD-process + ra-project)
    │
    ├── [찾음] ──► 팩트 + 출처 답변 → 완료
    │
    └── [못 찾음]
            │
            ▼
        사용자에게 미답변 고지
            │
            ▼
        ra-med-bot GitHub Issue 자동 등록
        라벨: needs-classification
            │
            ▼
        일일 배치 이메일 (08:00)
        수신: RA 담당자·관리자
            │
            ▼
        담당자 분류 판단
            │
            ├── [규제 지식 부족]
            │       │
            │       ▼
            │   ra-project GitHub Issue 등록
            │   → Cowork 스케줄 처리
            │   → ra-project 지식 보강
            │
            └── [사내 정책 부족]
                    │
                    ▼
                MD-process GitHub Issue 등록
                → Cowork 스케줄 처리
                → SOP·정책 문서 보강
                        │
                        ▼
                지식베이스 업데이트 완료
                    │
                    ▼
                이후 동일 질문 → 답변 가능
```

## 6. GitHub Issue 연계 구조

세 레포의 GitHub Issue가 하나의 추적 시스템으로 연결된다.

### Issue 흐름

```
ra-med-bot Issue (미답변 원본)
    │ 라벨: needs-classification
    │
    ├──► ra-project Issue (규제 지식 보강)
    │    라벨: ra-auto, knowledge-gap
    │    → Cowork EP 스케줄에 반영
    │
    └──► MD-process Issue (사내 정책 보강)
         라벨: policy-gap
         → Cowork 스케줄에 반영
```

### Issue 라벨 체계

| 라벨 | 레포 | 의미 |
|------|------|------|
| `needs-classification` | ra-med-bot | 미답변 발생, 담당자 분류 대기 |
| `knowledge-gap` | ra-project | 규제 지식 누락으로 분류됨 |
| `policy-gap` | MD-process | 사내 정책 누락으로 분류됨 |
| `ra-auto` | ra-project | Cowork 자동 처리 대상 |
| `resolved` | 모두 | 지식베이스 보강 완료 |

## 7. 알림 시스템

### 일일 배치 이메일 (08:00)

- 수신자: RA 담당자·관리자
- 내용: 전날 발생한 미답변 목록, 질문 내용, 발생 건수
- 발송: 워크스테이션 n8n 스케줄러
- 형식: 분류 판단에 필요한 최소 정보 포함

### 분류 판단 후 처리

담당자가 이메일 확인 후 해당 레포 GitHub Issue에 분류 라벨 추가 → Cowork 자동 감지 → 처리

## 8. 대화 이력·감사 추적

### 목적

내부 운영 기록. 규제 심사와 무관.

### 활용

- 미답변 패턴 분석 → ra-project BACKLOG 우선순위 반영
- 질문 빈도 높은 주제 → 지식베이스 우선 보강
- 내부 EP 스케줄(완성도 중심) + bot 미답변 BACKLOG(현장 긴급도 중심) 상호 보완

### 보관

- 워크스테이션 PostgreSQL 내부 테이블
- 외부 전송 없음

## 10. 지식베이스 성장 사이클

```
사용자 질문
    │
    ▼
미답변 감지
    │
    ▼
이메일 알림 → 담당자 분류
    │
    ▼
GitHub Issue → Cowork 처리
    │
    ▼
지식베이스 보강 (ra-project / MD-process)
    │
    ▼
GitHub 동기화 → pgvector 재ingestion
    │
    ▼
이후 동일 질문 → 답변 가능
    │
    └─────────────────────────────► 사이클 반복
```

사용자의 질문이 쌓일수록 지식베이스가 성장하고, bot의 답변 가능 범위가 확장된다.

## 11. 외부 리서치 원칙

내부 지식베이스에 없는 내용에 대해 외부 리서치가 필요한 경우:

### 허용 소스 (공신력 있는 공식 출처만)

| 지역 | 소스 |
|------|------|
| 국내 | MFDS 공식사이트 (mfds.go.kr) |
| 미국 | FDA.gov, eCFR.gov |
| 유럽 | EUR-Lex, European Commission |
| 국제 표준 | ISO, IEC 공식 사이트 |

### 원칙

1. 외부 리서치 결과는 **RA 담당자 검증 필수**
2. 검증 전 bot 답변으로 사용 불가
3. 검증 완료 후 ra-project에 저장
4. 이후부터 내부 지식으로 답변 가능
